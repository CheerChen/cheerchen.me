LLM のリバースエンジニアリングや自動化処理の能力を実際に触っていれば、こういう結果になるのも別に不思議ではありません。AI の普及で誰の手にも AK47 が配られたような状態になっており、この手の漏洩は今後ますます日常茶飯事になるはずです。

自分のパスワードマネージャーを棚卸ししてみると、一度きりのつもりで登録した日本の Web サイトのアカウントが 100〜200 件以上眠っていました。普段から 1Password や Bitwarden を使ってサイトごとに別々のランダムパスワードを設定しているので、パスワードリスト型攻撃は心配していません。本当に厄介なのはアカウント内に残っている個人情報のほうで、大半に本名や住んでいた実際の住所を入れており、一部にはクレジットカードまで紐づいていました。2 年ほど前に友人と似たような話をした際、「日本はオフラインの手続きでも毎回本名や現住所を求められるから、オンライン側で一度漏れると逃げ場がないよね」と言っていたのですが、見事にその通りになってしまいました。

企業側が攻撃されて DB ごと抜かれるのを防げない以上、こちらでできる自衛は、こうした「一時利用」のアカウントに残った個人情報を洗い流すことくらいです。

- **氏名・住所・電話番号を、あらかじめ用意したダミーのプロフィールに書き換える**
- **ログイン用メールアドレスを、bot 専用の受信箱に統一する**
- **登録済みのクレジットカードを削除し、外部アカウント連携を解除する**
- **ついでにメルマガ購読を止め、退会可否と退会ページの URL を控えておく**

> [!TIP]
> なぜ最初から退会（アカウント削除）を申請せず、個人情報の書き換えを選んだのか？
>
> 日本の Web サイトでは、退会手続きをしても過去のデータが裏側の DB に残ったままになるケースが少なくありません。データ保持ポリシーを理由に一定期間ユーザーの情報を残したり、単なる論理削除（ソフトデリート）で済ませたりするサイトもあるため、単に退会するより先に登録情報をダミーで上書きしてしまうほうが確実です。

ただ、これを 1 サイトずつログインして会員情報変更ページを探し、認証コードを受け取ってフォームを書き換え、さらに Bitwarden に書き戻すとなると、手作業では到底終わりません。

ちょうど最近 Grok Bot を使い始める人が増えていたので、この一括クリーニングを任せてみることにしました。ついでに、どこまで使い物になるのか試すのにも良い題材です。

## TL;DR

最終的に一番スムーズだった構成は、Grok Bot を調整役に置き、実行はローカルのヘッドレスセッション（コストが読めるモデルが望ましい）と `ego-browser` に任せる形でした。

合計で約 100 件のレコードを処理し、8 割以上のアカウントで個人情報の書き換えを完了できました。

ただし、「完全放置で自動実行」とは程遠く、実際には人間の介入がかなり必要でした。私が途中で手を動かしたのは主に次の 3 つです。

- チャット画面から Grok Bot を起こす（理由は後述）
- スマホに届く SMS 認証コードや、元のメールアドレスに届く確認コードを中継する
- パスワード不一致やサイトの不正ログイン対策で弾かれたときに引き継ぐ

以下、ステップごとに書いていきます。

## ステップ 1：bot に台帳を渡す

{{< figure src="bitwarden-prefix-list.png" >}}

最初にやったのは、処理対象のアカウント一覧を bot が直接取得し、処理状況を自分で記録できる仕組みを作ることです。
ここでは Bitwarden CLI（以下 `bw`）を使いました。

手順はシンプルです。

- bot 専用の Bitwarden アカウントを新規登録する
- メインアカウントから bot を Organization に招待する
- クリーニング対象のアカウントを Organization の Collection に割り当てて共有する
- bot に直接 `bw` コマンドを叩かせる

各アカウントの処理を始める際に bot が `bw get item` で項目を取り出し、Web サイト側の書き換えが終わったら `bw edit item` で結果を Vault に書き戻します。

> [!TIP]
> ここのコツは、アイテム名の先頭に角括弧のプレフィックスを付けて現在のステータスを表すことです。先頭に `【】` が付いていなければ未処理、と一目で判別できます。このルールにしておくと、新しく引き継いだエージェントも Bitwarden の一覧を取り直して角括弧付きの項目を除外するだけで同じキューの続きから走れるため、人間が途中で突合する必要がなくなります。

プレフィックスの分類と判定基準は、最終的に次の 5 種類に固定しました。

| プレフィックス | 意味 | 最終件数 |
|---|---|---:|
| `【已清洗】`（クリーニング済） | 個人情報を置換済み。一部変更不可の項目がある場合は備考に理由を記載 | 83 |
| `【已退会】`（退会済） | 退会完了、または旧アカウント自体がすでにログイン不可 | 11 |
| `【代注册】`（代理登録） | 最初から bot がダミー情報で登録したアカウント | 3 |
| `【未完成注册】`（登録未完了） | 昔登録した際にフローを最後まで完了していなかったアカウント | 2 |
| `【无需清洗】`（対象外） | 内容を確認した上でそのまま残すと決めたアカウント | 2 |

## ステップ 2：現実的なゴール設定

### 最小変更の原則と変更不可項目への対処

実際に回してみると、会員マイページから特定の項目を自分で変更できないサイトが結構あります。「全項目の完全書き換え」を唯一の完了条件にしてしまうと、エージェントが画面上で無限ループに陥ります。

そこで、「氏名・電話番号・住所など変更可能な項目をすべて書き換え、Bitwarden の `notes` に『メールアドレスは読み取り専用』『変更はサポート窓口への連絡が必要』と明記すれば、`【已清洗】` を付けてよい」というルールに緩めました。

また、最小変更の原則として、もともと空欄だった任意項目は空欄のままにし、本物の情報が入っていた項目だけを上書きします。

連絡先は bot 専用の受信箱や予備の電話番号を優先して入れ、変更後の値を Bitwarden 側にも同期させました。

### 共通 ID の分割

もう一つ厄介だったのが、複数サイトで同じ共通 ID・会員基盤を使っているケースです。

Bitwarden 上の 1 アイテムとしてそのままクリーニングを依頼すると、同じ ID でログインできる別サイト（プロフィールのテーブルが別になっているもの）が未処理のまま漏れてしまいます。

この手のアカウントに当たったら、まず bot に Bitwarden 上でアイテムを複製させ、アイテム名をサブサイトのページタイトルに書き換えてから、別個にキューへ戻して洗わせるようにしました。

### 注文中・チケット・金融・通信・インフラ系はスキップ

本人確認が絡むサービスは、エージェントにリスクを警告させ、手動で `【无需清洗】` を付ける運用にしました。

渡したプロンプトは次のような内容です。

> 「チケット販売、金融、KYC 済みの暗号資産、通信キャリア、公共料金、および本人確認が義務付けられているフリマ・中古買取サービスに関わる場合は、すべて先に実名確認リスクとしてフラグを立て、私が 1 件ずつ確認するまで実行を止めること。」

ここを無邪気にダミー情報へ書き換えると、発券済みのチケットが無効になったりアカウントが凍結されたりする恐れがあるためです。

## ステップ 3：プラットフォームの安全審査ブロックへの対処

ここが最初にぶつかった壁でした。

当初はクラウドサンドボックス（box）の中だけで全工程を完結できるだろうと考え、Grok Bot の「登録アシスタント」にすべての操作を任せていました。

ところが、Grok Bot のクラウドサンドボックスにはブラウザタスク向けのプラットフォーム安全審査が入っています。この審査は、タスク指示文に含まれるアカウントのパスワードと、画面やスクリーンショット上に並ぶ大量の個人情報の 2 つを容赦なくブロックします。

しかも発動すると承認カードすら出さずにタスクを即座に強制終了するため、Auto-review の承認ルールを設定しても素通りできません。モデルに「パスワードを見せない」ままログインと情報変更をさせるため、パスワードの渡し方だけで 3 回やり直す羽目になりました。

### ログイン操作でいきなり強制終了

最初は、登録アシスタント bot に `bw` からパスワードを取り出させ、それをブラウザサブタスクの指示文に書いて入力させようとしました。

1 サイト目を走らせた時点で、アシスタントが内蔵ルールに従って `My rules don't let me enter a user's account password` と拒否してきました。管理画面でカスタムルールを追加して手動許可したところ、そのサイトには無事ログインできたのですが、続けて他のサイトを回すと 20 分の間に 3 つのブラウザタスクが立て続けにプラットフォーム側から強制終了されました。エラーメッセージはすべて同じです。

> `The helper was stopped because its request or an image in its conversation was blocked.`

{{< figure src="review-blocked-task.webp" title="ログインパスワードの入力を拒否・遮断し始めた Grok Bot のブラウザ" >}}

登録アシスタント自身も「このブロックは承認カードが出ないため、承認ルールでは回避できない」と判断していました。

そこで定期実行をいったん止め、別の「調査担当」bot に境界テストをやらせてみました。先ほど落ちた 3 サイトに対して「ログインページを開くだけでパスワードは入力しない」という指示に変えたところ、3 件とも最後まで止まりませんでした。つまり、プラットフォームの遮断を引き起こしていたのは「パスワードをタスク指示文に書いてブラウザアシスタントに入力させる」ステップだったわけです。

これを避けるには、ブラウザタスクのテキストにパスワードを出さず、Grok Bot ネイティブの自動入力を使うしかありません。しかし Grok Bot の自動入力は 1Password にしか対応しておらず、Bitwarden を読めません。

苦肉の策として、1Password を一時的な中継ブリッジにする方法をひねり出しました。トライアルアカウントを登録し、`Bridge` Vault と Service Account を用意します。

- `bw` で対象アイテムを取り出し、パーミッション `600` の一時テンプレートファイルに書き出す
- `op item create --vault Bridge` で 1Password 側に同期する
- ローカルの一時ファイルを `shred` で消去し、ブラウザ拡張の自動入力でログインと書き換えを済ませたら、最後に `Bridge` 内のアイテムを削除して `bw lock` を実行する

### 1Password 自動入力でも再びブロック

ところが、ログインを抜けて会員情報の編集ページを開き、いざ書き換えようとしたところで、開始 4 分ほどでまたタスクが強制終了されました。

調べてみると、今回もプラットフォーム審査に引っかかっていました。画面のスクリーンショットに本物の個人情報が大量に写り込んでいたためです。その後、スクリーンショットを撮らずテキストスナップショットだけを読む設定に変えてみても、ページ上に表示される氏名・電話番号・住所が多いサイトでは、編集画面を開いただけで次々と止められてしまいました。

さらに 1Password の自動入力自体も何度も詰まりました。

- **ログイン以外のフォームに入力できない**：`does not have a complete sign-in form with an eligible password field` というエラーが出て弾かれる
- **クリップボード経由の貼り付けが複雑で壊れやすい**：自動入力の制限を回避するため、コマンドラインで `Bridge` からパスワードを変数に取り出し、`DISPLAY=:4 setsid xclip -selection clipboard` でシステムのクリップボードに入れ、`computerUse` でパスワード欄をクリックして `Ctrl+V` で貼り付け、直後に `pkill xclip` でクリップボードを空にする、という曲芸のような手順を組む羽目になった
- **新規作成した bot で 1Password 連携を使い回せない**：残りのキューを捌くために「クリーニング担当」bot を新設し、10 ステップの標準フローと 19 項目のルールを書いた手順書まで用意したのですが、いざ自動入力を呼ぶと手動承認を求められた挙句 `could not resolve this login` で失敗。1Password を繋ぎ直してテストしても「新しく作った bot からはこの 1Password を使って入力できない」という結論になり、結局この bot は 1 アカウントも処理できないまま削除しました

---

ここまで来て、クラウドサンドボックスの限界がはっきりしました。

- **単一デスクトップ環境の制約**：サンドボックス内にデスクトップ環境が 1 つしかないため、すべてのブラウザ操作が直列待ちになり、とにかく遅い
- **トライアル枠がすぐ尽きる**：直列で少しずつ動かしても、トライアル枠では数アカウント分しか持たず、フローの検証くらいにしかならない
- **プラットフォーム安全審査が厳しすぎる**：ブラウザタスクが安全審査で頻繁に強制終了され、承認ルールでも制御できない

これでは 100 件規模のアカウントクリーニングには到底使えません。どうにかしてこの制限を外せないか考えました。

### ローカルのヘッドレスセッションへ切り替え

そこで方針を切り替え、肝心のブラウザ操作をすべて手元の Mac に引き戻すことにしました。ローカルには普段から使っている `ego-browser` とエージェントの実行環境が揃っているので、Grok Bot にはリモート側の調整役に徹してもらいます。

ローカルの作業ディレクトリに共通のルールをまとめた `task-template.md` を置き、ここまで踏んだ地雷や例外ルールをすべて書き込みました。各アカウントの処理は `claude -p` や `codex exec` のヘッドレスセッションを 1 アカウント 1 プロセスで立ち上げて実行し、終わったらステータスと変更項目だけを（パスワードを含まない）`result.json` に書き出します。最後にリモートの「調査担当」bot がそのファイルを読んで Bitwarden 側を照合・更新する流れです。

{{< figure src="sandbox-vs-home.svg" title="クラウドサンドボックスでの直列待ち・審査ブロックから、ローカル Mac での並列実行へ" >}}

{{< figure src="local-agent-pipeline.svg" title="ローカル Mac の並列ヘッドレスセッションとリモート Grok Bot の連携構成" >}}

実行経路からクラウドサンドボックスのブラウザタスクが消えたことで、作業をぶつ切りにしていたプラットフォーム審査は完全に起きなくなりました。パスワードもローカルの `bw` から直接取り出して使う形に戻り、1Password の中継も不要になりました。

手元の Mac 上でのパスワード入力は、単発実行と並列実行で 2 通りのやり方を使い分けました。

- **単発実行時は `pbcopy` で貼り付け**：`bw unlock --passwordenv BW_PASSWORD --raw` で取り出したパスワードを、macOS の `pbcopy` と `Meta+V` でパスワード欄に貼り付ける
- **並列化後はパーミッション `600` の一時ファイル + `page.fill`**：複数タスクを並列で走らせると Mac 全体で 1 つのシステムクリップボードを共有するため、直前のタスクがコピーしたパスワードを別のタスクが上書きしてしまいます。そこで並列実行時は、取り出したパスワードをパーミッション `600` の保護された一時ファイルに書き出し、ブラウザ駆動層がファイルから直接読んで `page.fill` で流し込む方式に統一しました

パスワード入力と安全審査の問題が片付いただけでなく、ローカルに移したことで嬉しい副産物が 2 つありました。

- **完全な「1 アカウント 1 セッション」と並列実行**：毎回まっさらなコンテキストで起動するため、前のサイトの残骸やエラーに引きずられません。単一デスクトップの直列制約もなくなったので複数プロセスを一気に並列実行でき、途中で詰まったアカウントも `sessions.tsv` に記録した session ID から `resume.sh` で個別に再開できます。
- **自宅回線による不正アクセス検知の回避**：通信元がクラウド事業者のデータセンター IP から自宅の光回線 IP に変わったことで、日本の Web サイト側でアクセス遮断や追加認証に引っかかる頻度が目に見えて減りました。

ただ、ローカルでこのパイプラインを回し始めてすぐ、別の問題にぶつかりました。並列実行によるトークン消費の激しさ（Codex）と、Claude Code 内蔵の権限ポリシーによるメールアドレス変更ブロックです。

## コストと権限：Codex・Claude Code から Devin SWE-2 へ

### 第 1 走者：Codex の利用枠が一瞬で枯渇

最初は `codex exec` に `--dangerously-bypass-approvals-and-sandbox` を付け、モデルに `gpt-5.6-sol` を指定して、起動タイミングを約 25 秒ずつずらしながら 5 アカウント並列で走らせました。

Codex の仕事ぶりは確かに手際がよく、再開分も含めて計 48 回の実行をこなしてくれました。しかし消費スピードが凄まじく、最初の 5 並列バッチを走らせただけで 5 時間利用枠の残量が一気に 0% まで溶けました。利用枠のリセットを 1 回使って 1 時間後に次のバッチを走らせたところ、また残り 21% ほどまで削られ、結局もう一度リセットを切る羽目になりました。

{{< figure src="codex-quota-depleted.png" >}}

あとからローカルに残っていたセッションログを集計してみると、13 セッションだけで合計 26,368,770 input tokens（うち 25,547,520 が cached input）と 185,707 output tokens を食っていました。1 セッションあたり 43〜60 分走り、それぞれ 495 万〜742 万 input tokens を消費していた計算になります。

### 第 2 走者：Claude Code は権限分類器に止められる

Codex の枠が持ちそうにないので、急いで Claude Code（モデルは `claude-sonnet-5-5`）も投入して負荷を分散させました。こちらも 5 アカウント並列で、計 12 セッション（累計で約 1,720 万 cache read tokens、132 万 cache write tokens）を回しました。

ところが、走り出してすぐに権限の罠を踏みました。ローカルの `settings.json` で `defaultMode=auto` を設定していたのですが、このモードはコマンドラインの承認バイパス指定よりも優先されます。そして内蔵の安全分類器が「認証情報を触っている」「アカウントに紐づくメールアドレスを変更しようとしている」と検知した瞬間、操作を拒否してしまいます。

たとえば無印良品（MUJI）の会員情報を洗っていた際、氏名や住所の変更まではすんなり通ったのに、登録メールアドレスを書き換えるステップに入った途端、分類器に `Account & Standing-Rule Changes` という理由で止められ、`partial`（中途半端な状態）で止まってしまいました。

{{< figure src="claude-muji-email-blocked.webp" title="MUJI の登録メールアドレス変更時に権限分類器でブロックされた Claude Code" >}}

### 第 3 走者：Devin SWE-2 でようやく完走

利用枠と権限の両方から挟み撃ちにされた末に目を付けたのが Devin CLI です。ちょうど `SWE-2` モデルがプロモーション期間中で、有料プランの会員なら無料で使えました。こうしたクリーニング作業なら、`SWE-2` でも十分こなせるのではないかと考えたわけです。

そこで Grok Bot に単一サイト起動用の簡単なスクリプト `devin-one.sh`（中身のコマンドは `devin --model swe --permission-mode bypass --respect-workspace-trust=false -p`）を書かせ、それを `devin-batch5.sh` のようなバッチスクリプトで束ねて、1 バッチあたり 5 アカウント並列で立ち上げるようにしました。
ブラウザ操作の層は skill 経由で `ego-browser` に渡し、Mac 上の実ブラウザを直接動かしています。

{{< figure src="devin-batch-terminal.webp" title="Devin CLI でバッチ並列実行しているターミナル出力" >}}

ここから一気に作業が軌道に乗りました。合計で 7 バッチ以上を回し、43 件の実行ログが残っています。

通常のアカウントであれば、ページを開いてからプロフィールを書き換え、Bitwarden に書き戻すまでの所要時間は中央値で 7〜15 分ほどに収まりました。

> [!NOTE]
> 振り返ってみると、ログインして会員情報を書き換える程度の定型作業には、飛び抜けて賢い推論モデルはそもそも必要ありませんでした。一番効いたのは、`ego-browser` skill を使ってローカルの実ブラウザ環境を動かし、サンドボックスの制約を丸ごと回避できたことです。

もちろん、Devin CLI + `ego-browser` の構成でも、いくつか実運用ならではの罠は踏みました。

- **一時サブシェルの終了に巻き込まれて子プロセスが死ぬ**：最初は一時サブシェル内で `nohup ... &` を使って Devin を起動していたのですが、外側のシェルが抜けた瞬間に配下の子プロセスまで道連れで kill され、ログファイルが空っぽになっていました。常駐のバックグラウンドシェル（`block_until_ms=0`）から直接起動する形に変えてようやく安定しました。
- **複数セッションから同じサイトを二重起動してしまう**：同じアカウントを別々のセッションから重複して立ち上げてしまい、後から片方を止めようとして実際に動いている側のプロセスを誤って kill してしまうミスがありました。以降は、すべての Devin タスクを単一の調整役 bot がプロセス一覧を確認してから起動するルールに統一しました。
- **`ego-browser` の `evaluate` がまれにハングする**：裏で動いている Node.js プロセスがときどき固まることがあり、手動で `kill -9` してやらないと Devin が先に進めない場面がありました。また、`ego` の `task.cdp` が `Browser.setPermission` に未対応だったためページ単位の `page.cdp` に切り替える必要があり、これもタスクテンプレートの「ego の既知の罠」セクションに追記しました。
- **無料期間終了後のコストが読めない**：`SWE-2` の無料キャンペーンがいつまで続くのかはっきりしておらず、ローカルのログにはトークン数も課金額も記録されないため、無料期間が終わったあとに同じ規模のバッチを回すと幾らかかるのかは今のところ見積もれません。

## 認証コードの受け渡し：human in the loop

bot 専用の受信箱へメールアドレスを変更するときや、電話番号を差し替えるときは、ほぼ確実にワンタイムパスワード（OTP）や確認リンク付きのメールが飛びますし、SMS 認証を求めてくるサイトも少なくありません。

問題は、自宅の Mac 上で走っているローカルの Devin プロセスからは、リモート側にある Grok Bot 専用のメール受信箱を直接読めないことです。毎回人間がコピペするのを避けるため、エージェント同士で認証コードを受け渡す約束事を決めました。

### ローカルファイルを介した受け渡し

受け渡しのプロトコル自体は 2 つのファイルを使うだけの簡単なもので、メール着信をトリガーに動くタスク（routine）と組み合わせることで、メール認証のステップを自動化できました。

{{< figure src="email-trigger-routine.webp" title="メール着信をトリガーに bot を起こす routine" >}}

- **ローカルの Devin が `need-otp.json` を書いて待機**：認証コード送信ボタンを押したら、そのサイトの作業ディレクトリに `need-otp.json`（サイト名、送信先の末尾番号やメールアドレス、要求種別、タイムスタンプ）を書き出し、ページをリロードせずその場で待機する
- **`otp.txt` のポーリングとタイムアウト再送**：Devin は同じディレクトリの `otp.txt` を 10 秒おきにチェックし、最大 10 分待つ。届かなければ再送してもう 1 ループ待つ
- **Grok Bot が受信箱を読んで `otp.txt` に書き戻す**：メール着信トリガーの routine を設定しておき、新着メールが届いたらリモートの「調査担当」bot を起こす。bot は Mac 側でどのサイトが `need-otp.json` を出しているか確認し、認証コードや確認 URL を抽出して対応する `otp.txt` に書き込む

この連携が一番きれいに決まったときは、Devin が送信ボタンを押してリクエストを書き出し、確認メールの着信で起きた bot がコードを `otp.txt` に書き込み、Devin がそれを読み取って画面に入力しメールアドレス変更を完了するまで、私が一度も手を触れずに完結しました。

{{< figure src="otp-handoff-files.webp" title="need-otp.json と otp.txt を介したローカル Devin と bot の認証コード受け渡し" >}}

### Grok Bot が「起きない」3 つのパターン

ただ、このメール認証の部分を除くと、マルチエージェント間の自動ウェイクアップは最後までうまく機能せず、結局ここが一番人手を食うポイントになりました。リモート側の bot を必要なタイミングで起こして働かせるだけでも、3 種類の「起きない」問題にぶつかりました。

- **自分で立てたバックグラウンドプロセスからは自分を起こせない**：bot 自身にバックグラウンドでタイマーやファイル監視スクリプト（毎分ポーリングする `watch.sh` など）を走らせても、メインセッションがいったんスリープに入ると、バックグラウンドスクリプトからはメインセッションを叩き起こせません。
- **定期実行タスク（routine）が遅延・スキップされる**：Grok Bot のプラットフォーム標準の定期実行タスク（5 分おきに回る監視 routine）は、高負荷時に平気で遅れるうえ、ときにはスキップされます。
- **定期実行タスクの終了時に Devin まで道連れで kill される**：定期実行タスクの一時シェルから直接立ち上げた Devin プロセスは、その routine の実行ターンが終わった瞬間にシステム側からまとめて kill されてしまいます。

要するに、現状の Grok Bot には継続的に自律稼働する仕組みがまだ整っていません。今振り返ると、実行役を Devin CLI + `ego-browser` に任せつつ、進捗監視と調整役にはローカルの Claude Code を使ったほうがずっと安定したはずです。

> [!TIP]
> 途中で、異なるマシン上のエージェント同士でメッセージ送信やウェイクアップを行うコミュニティ製ツール `yobiru` を「調査担当」bot に勧めてみたのですが、自分で調べに行った結果なぜか導入を却下してしまい、マルチエージェントのウェイクアップ問題を本当に解決できるかは未検証のまま残っています。ここは今後改善できる余地があります。

## おわりに

20 時間以上かけて Grok Bot やローカルエージェントと格闘し、100 件を超えるアカウントを洗い終えてみると（正直、手で 1 個ずつ直したほうが早かった気もしますが）、確かな収穫が 2 つありました。

- **一括クリーニングのパイプラインを実用レベルまで通せたこと**：クラウドサンドボックスの安全審査、トークン枠の枯渇、権限ブロック、リモート側のウェイクアップ不全とあらゆる地雷を踏んだものの、最終的には複数サイトの面倒なフォーム書き換えを bot で一括処理できると実証できました。あわせて、「Bitwarden のプレフィックスによるキュー管理 + パスワードは会話に乗せずローカル直読み + 手元の実ブラウザで並列実行 + ローカルファイルでの OTP 受け渡し」という再利用可能な型も固まりました。
- **実際の個人情報漏洩を間一髪でやり過ごせたこと**：10 月 23 日、グッドスマイルカンパニー（GSC）公式ショップが不正アクセスの発表を出しました。10 月 19 日午後から 22 日夜にかけて管理画面へ繰り返しアクセスがあり、会員の氏名・住所・電話番号・メールアドレス・注文履歴が閲覧された可能性があるとのことです。私もそこにアカウントを持っていたのですが、ちょうど数日前にクリーニング対象リストに入っており、bot が一通りダミー情報へ書き換えた直後でした。

もちろん、過去に作ったアカウントを後から洗って回るのは所詮「事後対応」でしかありません。

これだけ情報漏洩が頻発する状況で本当に手間を減らすなら、最初からゼロトラストの前提に立つしかありません。つまり、登録した瞬間から「このサービスに渡した情報は遅かれ早かれ漏れる」と決め打ちし、サービスごとの本人確認要件に応じて「デジタル上の分身」（ダミーのプロフィール、専用受信箱、予備の電話番号）を使い分けることです。渡す情報の蛇口を最初から絞っておくのが、結局一番現実的で、後からまとめて火消しに追われずに済む方法だと思います。
